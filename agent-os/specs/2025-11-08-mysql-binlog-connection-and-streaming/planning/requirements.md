# Spec Requirements: MySQL Binlog Connection & Streaming

## Initial Description
MySQL Binlog Connection & Streaming — Establish connection to MySQL server, configure binlog streaming with GTID support, and implement basic event reception loop with error handling and reconnection logic.

## Requirements Discussion

### First Round Questions

**Q1:** I assume we will use go-mysql (github.com/go-mysql-org/go-mysql) with GTID enabled and ROW binlog format already set on the MySQL server. Is that correct, or should we detect/validate these settings on startup?  
**Answer:** correct

**Q2:** I’m thinking we should configure secure connection options (TLS, timeouts, keepalive) and a bounded reconnect/backoff policy (e.g., exponential with jitter, capped at ~3s). Should we add TLS support now or defer it?  
**Answer:** use basic connection with user and password, exponential backup retry when connection failure with error log

**Q3:** For initial scope, I assume we only stream from a single primary instance (no replica/failover logic) and do not manage GTID persistence yet (covered by later roadmap items). Correct?  
**Answer:** correct

**Q4:** On reconnect, I assume we reattach using the last known GTID from in-memory state for this session only (no durable resume). Should we fall back to current master position if GTID is absent?  
**Answer:** yes, we can use in-memory GTID for this state

**Q5:** For resource limits, I propose controlled fetch loop with context cancellation, a small internal buffer, and metrics for connection status and event fetch errors. Is a minimal set of metrics acceptable for now (connection_state, transient_errors_total)?  
**Answer:** sounds good, do reuse or merge with existing code under binlog package

**Q6:** Logging: I’ll keep concise info/warn/error logs (no secrets in DSN), and ensure errors have actionable context. Is DSN redaction required or will DSN be provided via env vars without credentials in logs?  
**Answer:** don't use DSN, just state databse in log, there will only be 1 database connecting so the debug won't be hard

**Q7:** Configuration: Use env variables for host, port, user, password, TLS mode, and connect timeouts. Do you want a single env prefix (e.g., KVF_MYSQL_*) and a default 5s connect timeout?  
**Answer:** port can be fixed to 3306; host, user, and password should comes from a json file generated by hashicorp vault agent

**Q8:** Exclusions: Anything we should explicitly defer (e.g., multi-source replication, schema/table filters, IAM auth, advanced TLS validation)?  
**Answer:** only support single source, no IAM, to TLS validation. There's a METADATA_TABLE in mars-lib library that should be filter out, we only want the changes from tables with prefix defined by CONFIG_DATA_TABLE_PREFIX in mars-lib

## Requirements Summary

### Functional Requirements
- Establish a MySQL binlog connection using go-mysql with GTID/ROW already configured on the server.
- Connect with username/password from Vault-provided JSON (fixed port 3306).
- Maintain streaming loop with exponential backoff retry, logging connection failures.
- Track in-memory GTID for reconnects during the process lifetime; fall back to master position if none captured.
- Filter out `METADATA_TABLE` and only process tables with `CONFIG_DATA_TABLE_PREFIX` prefix.
- Emit minimal metrics for connection state and transient errors, leveraging existing binlog package utilities.
- Provide an application entry point (`main.go`) that loads configuration, initializes the connection, wires streamer → coordinator → aggregator, and starts streaming.

### Reusability Opportunities
- Reuse existing code in `internal/binlog/` for retry logic, logging, and stream handling.
- Align new connection manager with patterns already used in the binlog streamer.

### Scope Boundaries
**In Scope:**
- Single-source MySQL connection with username/password authentication.
- Exponential backoff retry on connection failures.
- In-memory GTID tracking for this runtime.
- Minimal logging/metrics aligned with mars-lib logger and observability package.

**Out of Scope:**
- TLS support and IAM authentication.
- Durable GTID persistence or resume across restarts.
- Multi-source replication or failover management.
- Advanced table filtering beyond prefix-based inclusion/exclusion already defined.

### Technical Considerations
- Credentials sourced from a Vault agent JSON file; avoid DSN logging, only mention database.
- Fixed port 3306; host/user/password loaded from file.
- Merge with existing `internal/binlog` structures to avoid duplication.
- Ensure METADATA_TABLE from mars-lib is excluded; only CONFIG_DATA prefixed tables streamed.
- Entry point should bootstrap logging/metrics, invoke connection setup, and handle graceful shutdown (context, signal handling) for the streaming + aggregator pipeline.
